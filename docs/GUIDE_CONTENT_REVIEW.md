# Разбор уроков Маршрута и план улучшений

Подготовлено 04.10.2026 в Cowork. Прочитаны все 31 урок из `public.guide_steps` и ключи проверок из `private.guide_checks`. Факты сверены с документацией Claude Code (code.claude.com/docs) и CHANGELOG (последний релиз — v2.1.288) на 04.10.2026.

Задание для Code-сессии: сначала раздел 1 (ошибки), затем раздел 2 (проверки), затем пилот нового формата на одном уроке (раздел 5) и показ владельцу. Раскатывать на все уроки только после его одобрения.

Порядок правки контента — как в `docs/GUIDE_PLAN.md`, раздел «Editing content»: исходник `content/guide/<step-id>.ts` → `npm run guide:content -- <step-id>` → миграция → проверки → `apply_migration`. Решения владельца из `docs/GUIDE_PLAN.md` (только выбор вариантов, без свободного ввода; без публичного профиля и показа прогресса; формулировка роли) важнее этого разбора. Если предложение здесь с ними расходится, следуй им и скажи владельцу.

## 0. Общая оценка

Основа сильная. Есть единый формат (результат, время, сравнение «до / после», симуляция сеанса, ловушка и совет, практика с критериями, проверка с объяснением каждого варианта), перекрёстные ссылки между шагами, хорошая русская типографика, а почти все факты подтверждаются документацией.

Чтобы курс воспринимался как лекции эксперта, а не как выжимка из документации, не хватает четырёх вещей:

1. **Своего голоса.** Все 31 урок построены по одной схеме и заканчиваются парой «ловушка + совет». Ссылка «документация говорит / советует» встречается 23 раза в 17 уроках: авторитет передан документации, а не автору.
2. **Объяснения механики.** Уроки говорят, *что* делать, но редко объясняют, *почему* агент ведёт себя именно так. Опытному разработчику модель поведения важнее списка команд.
3. **Связи с опытом аудитории.** Читатель годами писал код вручную, а уроки почти не опираются на то, что он уже умеет: ревью, RFC, онбординг новичка, pre-commit-хуки.
4. **Активной практики внутри урока.** Пока урок — это чтение и проверочные вопросы. Данные для интерактива уже есть: пометки в diff, решения в симуляциях.

## 2. Проверки (квизы): дыра в формате

Данные из базы: 85 вопросов, из них 75 с одним ответом.

- **В 74 из 75 вопросов правильный ответ стоит первым, и интерфейс его не перемешивает** (`src/features/guide/lesson/Check.tsx`: `question.options.map` выводит варианты в исходном порядке). Проверку проходят вслепую, нажимая первый вариант. Нужно детерминированное перемешивание на клиенте (по `user_id + question_id`, чтобы порядок не прыгал при перезагрузке) и тест на него. Ключи остаются на сервере, так что перемешивание ничего не раскрывает.
- **В 53 из 85 вопросов правильный ответ самый длинный.** Это классическая подсказка, её ловят даже без чтения урока. Выровнять длину вариантов: дистракторы должны быть такими же подробными и правдоподобными.
- **Вопросы на запоминание** («Что делает `/code-review`?», «Как посмотреть стоимость?», «Что делает `opusplan`?») заменить ситуациями с выбором решения, как в лучших вопросах курса («Агент уверенно описал `applyPromo()`. Что делаете дальше?»).
- Объяснения к каждому варианту (`why`) — сильная сторона, сохранить.

## 3. Как сделать уроки интереснее и квалифицированнее

По приоритету: P1 — основа нового формата, P2 — заметный рост качества, P3 — шлифовка.

### 3.1 P1. Блок «Как это сделано здесь»
Самый сильный и самый редкий ход курса уже присутствует в двух уроках: «почти такой же хук работает в проекте, где пишется этот курс». Его стоит сделать сквозным: в каждом этапе — реальный артефакт из репозитория agentica.
- Этап 2: настоящий `CLAUDE.md` проекта и почему в нём именно эти строки.
- Этап 3: задание на зону участников, переданное из Cowork в Code-сессию файлом (`docs/MEMBERS_AREA_PLAN.md`, сейчас он заменён `docs/GUIDE_PLAN.md`, но есть в истории git). Это передача задачи между сессиями, сверка с кодом в plan mode, пометки **[согласовать]**.
- Этап 4: реальный случай, когда ревью или хук что-то поймал.
- Этап 5: Supabase MCP в этом проекте. Сначала он был подключён только на чтение. Потом владелец осознанно дал запись, потому что проект тестовый, и закрепил в CLAUDE.md правило «схема и данные меняются только файлами миграций, по одному, по порядку». Готовый урок про области действия и права MCP на живом примере.
- Этап 6: две сессии, лендинг и кабинет, и как избежали конфликтов.

**Правило:** только правда. Каждое утверждение о собственном процессе сверять с историей git и владельцем.

Почему это работает: читатель видит, что автор делает то, чему учит. Для работодателя это самое прямое доказательство уровня.

### 3.2 P1. Блок «Почему так»: механика вместо правил
В каждом уроке 2–4 предложения о том, что происходит внутри. Без мистики и без преувеличений: только то, что подтверждается документацией или общеизвестными свойствами языковых моделей.
- 1.3: почему агент уверенно описывает несуществующее. Модель достраивает самое вероятное продолжение, а «уверенный тон» — свойство текста, а не знания.
- 2.1: почему длинная сессия «глупеет». Внимание распределяется по всему окну, ранние инструкции конкурируют с тысячами строк вывода, а сжатие теряет детали.
- 4.2: почему агент подгоняет тесты. Задача «сделай зелёным» буквально выполнима и через ослабление проверки.
- 6.3: почему ревьюер в чистом контексте полезнее. Он не унаследовал допущений, которые автор уже принял.

### 3.3 P1. Блок «Вы это уже умеете»: мост от опыта
Аудитория — опытные разработчики. Каждый урок стоит связать с практикой, которую они знают:

| Урок | Знакомая практика |
|---|---|
| 1.3 Агент как исследователь | Первая неделя в чужом проекте: вопросы старожилу |
| 2.2 CLAUDE.md | Онбординг-документ для нового сотрудника |
| 3.1 Анатомия задачи | Хорошо написанный тикет с acceptance criteria |
| 3.2 План до кода | Design review / RFC до реализации |
| 4.1 Чтение diff | Ревью PR джуниора, который пишет быстро и уверенно |
| 4.3 Тесты как контракт | TDD |
| 5.1 Хуки | pre-commit и обязательные проверки в CI |
| 6.1 Субагенты | Делегирование с узким брифом |
| 6.3 Роли | Разделение автора и ревьюера, «четыре глаза» |

Почему это работает: материал усваивается быстрее, а читатель видит, что его опыт не обесценился, а стал основой новой роли. Это и есть главный посыл сайта.

### 3.4 P2. Тренажёры внутри урока
Данные уже есть, нужен только интерфейс:
- **«Найди проблему» в diff** (4.1, 4.2, 4.4). Сейчас `DiffView.tsx` показывает пометки `mark` сразу, то есть ответ виден до того, как читатель подумал. Скрыть их, читатель кликает подозрительные строки (это выбор, а не свободный ввод), затем пометки раскрываются. Ровно тот навык, которому учит этап 4.
- **«Найди допущение» в плане** (3.2). Читатель видит план агента и до раскрытия отмечает пункт, который одобрять нельзя.
- **Развилка в симуляции** (3.4, 1.4). В момент, когда агент свернул не туда, читатель выбирает: Esc, отклонить с комментарием или дождаться конца. Каждый выбор показывает последствия.

### 3.5 P2. Учебный репозиторий-полигон
Этап 0 убрали, а с ним «учебный полигон». Практика сейчас требует собственного рабочего проекта, но многим нельзя запускать агента на рабочем коде (политика компании) или нет подходящего проекта. Решение — открытый учебный репозиторий с заложенными задачами под каждый этап: ослабленный тест, эндпоинт без проверки прав, раздутый CLAUDE.md, задача без критерия. Тогда практика воспроизводима, а её критерии объективны.

### 3.6 P2. «Проверить себя и пропустить»
Для опытной аудитории: пройти проверку до чтения урока. Все ответы верны — шаг засчитывается как «уже умею». Уважает время эксперта и делает статус «уже умею» честным.

### 3.7 P2. Честное время и разнообразие формы
- **Два времени:** «Чтение 12 мин · Практика ~1 час». Сейчас указано только чтение, а практика местами занимает день («проведите день по правилу…») или неделю («неделю смотрите `/usage`»).
- **Начало с крючка, а не с определения.** Конкретная сцена или заблуждение (пример в разделе 5).
- **Не каждый урок по одной схеме.** Пара «ловушка + совет» в конце каждого урока к пятому уроку становится предсказуемой. Варианты: урок-расследование (разбор провалившейся сессии), урок-тренажёр, урок-кейс.
- **Источники в конце урока, а не в тексте.** Вместо 23 «документация говорит» — блок «Источники» со ссылками на нужные страницы code.claude.com. Квалифицированная лекция ссылается на источники, но говорит своим голосом.

### 3.8 P3. Шлифовка
- **Итог этапа:** в карточку «Этап пройден» добавить короткий список «Что вы теперь умеете» (без свободного ввода, по решению владельца).
- **Пометка версии** в каждом уроке. Поле `verified` в исходниках уже есть, стоит показывать его читателю: «Проверено на Claude Code 2.1.x, октябрь 2026». Правило: при выходе новых версий Claude Code уроки перепроверяются (можно сделать навыком или scheduled task).
- **Финал маршрута** заслуживает момента: личный экран итогов (этапы, даты, результаты проверок) только для самого участника, без публикации и показа (решение владельца).

## 5. Пример: как может звучать урок 3.2 «План до кода»

**Сейчас** урок начинается так: «Агент пишет код быстрее вас. Поэтому его самая дорогая ошибка — не опечатка, а неверное допущение…»

**Предлагается:**

> **Крючок.** Пятница, 17:50. Агент закончил скидки: двенадцать файлов, тесты зелёные. В понедельник партнёрская выгрузка отправляет клиентам цены со скидкой как базовые. В коде ошибки нет. Ошибка в допущении: агент решил, что поле `price` читает только корзина.
>
> **Вы это уже умеете.** Перед большой фичей вы пишете RFC или собираете design review: подход обсуждается, пока изменение стоит минуту. План агента — тот же RFC. Черновик за полминуты пишет агент, а рецензент — вы.
>
> **Почему так.** Агент видит только то, что прочитал. Если в окне нет сведений о том, кто ещё использует `price`, он заполнит пробел самым вероятным предположением и дальше будет уверенно строить на нём: код получается непротиворечивым, хотя исходное допущение неверно. План выносит допущения наружу, где их видно вам.
>
> *(дальше — текущий материал урока: режим планирования, что читать в плане, симуляция)*
>
> **Тренажёр.** Вот план агента из пятничной истории. Отметьте пункт, который нельзя одобрять. *(после ответа раскрывается: «Пересчитать поле price» — его читает партнёрская выгрузка)*
>
> **Как это сделано здесь.** Зона участников этого сайта начиналась с задания файлом. Первым делом сессия сверила его с текущим кодом в plan mode, и реализация началась только после согласования. **[проверить у владельца, как было на самом деле]**
>
> **Источники.** code.claude.com/docs/en/permission-modes · /common-workflows

Объём урока растёт примерно на треть, и это нормально, если время чтения указано честно.

## 6. Порядок работы

1. **Исправления из раздела 1** — в исходниках `content/guide/<step-id>.ts`, затем `npm run guide:content -- <step-id>` для каждого изменённого урока и обновление `verified`. Перед правкой сверь каждый пункт с документацией (агент `claude-code-guide`): она меняется быстро.
2. **Проверки:** выяснить, перемешивает ли интерфейс варианты. Если нет — добавить детерминированное перемешивание. Затем выровнять длину вариантов и заменить вопросы на запоминание.
3. **Пилот:** урок 3.2 в новом формате (раздел 5) с новыми типами блоков `hook`, `bridge`, `why`, `here`, `sources` и тренажёром «найди проблему». Показать владельцу на desktop.
4. **После одобрения:** этап 1 целиком, затем остальные.
5. **Отдельно, с владельцем:** решить про учебный репозиторий (3.5) и разделы из раздела 4.
6. Миграции — через Supabase MCP по правилам из CLAUDE.md и `docs/GUIDE_PLAN.md`: `apply_migration`, по одному файлу, по порядку, сверка md5 строк с локальной сборкой PGlite, `get_advisors`.
