# Подключение Google-входа

Код приложения готов к подключению Supabase. Создание облачных проектов требует входа владельца в соответствующие аккаунты. До выполнения этих шагов реальный Google-вход недоступен; лендинг продолжает работать.

## 1. Создайте Supabase

1. Откройте [Supabase Dashboard](https://supabase.com/dashboard), создайте организацию и проект `agentica`. Выберите подходящий регион. Пароль базы сохраните у себя: приложению он не нужен.
2. В настройках проекта скопируйте **Project URL** и **Publishable key** (`sb_publishable_…`). Не используйте Secret key или старый `service_role`.
3. В **Authentication → Sign In / Providers → Google** найдите callback вида `https://<project-ref>.supabase.co/auth/v1/callback`. Он понадобится Google Cloud.
4. Включите создание новых пользователей; отключите анонимный вход и ненужные способы входа. Наш интерфейс использует только Google.


## 2. Создайте Google OAuth client

1. Откройте [Google Cloud Console](https://console.cloud.google.com/), создайте проект `agentica`.
2. В **Google Auth Platform** заполните Branding: название приложения, email поддержки и контактный email владельца.
3. В Audience выберите **External**. Приложение не ограничивает домены Google-аккаунтов. Если консоль ограничивает доступ тестовым списком в режиме Testing, добавьте аккаунты для проверки; для остальных пользователей выполните требования Google к публикации OAuth-приложения. Это отдельно от публикации самого сайта.
4. В Data Access используйте только `openid`, `.../auth/userinfo.email` и `.../auth/userinfo.profile`. Доступ к Gmail API не нужен.
5. В Clients создайте OAuth client типа **Web application**.
6. Authorized JavaScript origins: `http://localhost:3000` и `http://localhost:3001`. При использовании другого локального порта добавьте его точный origin.
7. Authorized redirect URIs: callback **Supabase** из шага 1, например `https://<project-ref>.supabase.co/auth/v1/callback`.
8. Скопируйте Client ID и Client Secret в настройки Google-провайдера **Supabase**, включите провайдер и сохраните. Client Secret не помещайте в код, `.env.local` фронтенда или чат.



## 3. Разрешите возврат на сайт

В **Supabase → Authentication → URL Configuration**:

- Site URL: `http://localhost:3000`.
- Redirect URLs: `http://localhost:*/auth/callback` (только для локальной разработки).

Цепочка переходов: **сайт → Supabase → Google → callback Supabase → `/auth/callback` сайта**. Приложение использует текущий origin, включая резервный порт. Для Google-входа открывайте именно `localhost`, а не LAN IP из вывода Vite. В production нужны HTTPS и точные разрешённые адреса вместо локального wildcard.

## 4. Создайте закрытый контент

В SQL Editor проекта выполните содержимое [миграции](../supabase/migrations/202609240001_member_content.sql) **один раз**. Она создаёт таблицу `member_content`, запись «тест контент», права чтения и RLS. Запись из браузера запрещена, гостям данные недоступны. Повторно выполнять создание таблицы не нужно.

Профиль хранится в Supabase Auth: `user_metadata.display_name` — имя для сайта; email и фото приходят из Google. Отдельная таблица профилей не требуется.

## 5. Подключите локальное приложение

Скопируйте `.env.example` в `.env.local` и заполните:

```dotenv
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_<your-public-key>
```

Перезапустите **свой** dev-сервер: `npm run dev` (`npm.cmd run dev` в PowerShell). Откройте адрес `Local` из терминала. Значения `VITE_*` доступны браузеру; защита данных обеспечивается проверкой сессии Supabase, правами таблицы и RLS.

## 6. Проверьте настоящий вход

1. В чистом профиле браузера откройте `/content`: должен появиться экран входа без закрытого текста.
2. Нажмите «Продолжить с Google». После согласия Google вы должны вернуться на `/content`, увидеть «тест контент» и меню аккаунта. Проверьте запись пользователя в Supabase Authentication.
3. В «Профиль» измените имя, сохраните, перезагрузите страницу. Имя должно сохраниться и отображаться в меню.
4. Откройте сайт во второй вкладке, выйдите в первой. Меню и закрытый контент должны исчезнуть в обеих вкладках.
5. Войдите повторно: аккаунт не должен дублироваться, имя для сайта должно сохраниться. При необходимости проверьте второй Google-аккаунт: его имя независимо.
6. Отмените Google-вход: приложение должно показать возможность повторить попытку.
7. Проверьте OAuth на портах 3000 и 3001. Не запускайте второй сервер без необходимости; после проверки остановите только свои процессы.

## 7. Проверьте доступ к данным напрямую

Гостевой запрос без сессии:

```sh
curl "https://<project-ref>.supabase.co/rest/v1/member_content?select=slug,body" -H "apikey: <publishable-key>"
```

Ожидается отказ в доступе, без текста записи. Для проверки вошедшего пользователя откройте DevTools → Network на `/content`, найдите запрос `member_content` и повторите его через **Copy as fetch** в консоли того же браузера: чтение должно вернуть запись. Удалите из копии заголовок `Authorization` и повторите — данные больше не должны возвращаться. Не передавайте и не сохраняйте токен из этого запроса в репозитории или чате.

Автотесты браузера используют фиктивный сервер через перехват запросов. Они не заменяют эти проверки реального проекта, Google OAuth и серверных прав.

## Если что-то не работает

- **Вход временно недоступен:** проверьте обе переменные, тип ключа и перезапуск Vite.
- **redirect_uri_mismatch:** в Google нужен callback Supabase, а не адрес локальной страницы.
- **Возвращает на другой порт:** проверьте Redirect URLs Supabase и открывайте сайт через `localhost`.
- **Вход не завершён:** повторите вход в том же браузере; PKCE использует локально сохранённый код проверки. Не очищайте данные сайта между переходами.
- **Контент не загружается после входа:** проверьте, выполнена ли миграция и есть ли запись со `slug = 'test'`.

Официальные инструкции: [Google в Supabase](https://supabase.com/docs/guides/auth/social-login/auth-google), [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
